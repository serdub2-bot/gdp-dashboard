# dbpatch — патчер базы FM2008

Код для работы с `*.dat` базы Football Manager 2008: чтение контейнера, сверка,
безопасные правки на уровне байтов и поиск соревнований по названию.

Всё проверено на реальной базе **8.0.2** из папки `db` (файлы из `inbox/1.zip … 4.zip`).

## Почему база не помогала: список дивизионов зашит в fm.exe

Проверено на самой игре 8.0.2. Для каждой страны в `fm.exe` есть функция,
которая регистрирует играбельные дивизионы по порядку:

```asm
push 0              ; флаги
push 1              ; ступень
push 0x1fdb7        ; id = 130487 «Россия. Первый дивизион»
mov  ecx, <нация>
call 0xd63c10       ; регистрация дивизиона
```

Вызовов столько, сколько играбельных ступеней у страны:

| Страна | Зарегистрировано | Ступени |
|---|---|---|
| Англия | 6 | Премьер, Первый, Второй, Третий, Конференция, Конференция Север/Юг |
| Испания | 3 | Первый, Второй, Второй B |
| Германия | 3 | Бундеслига, Второй, Региональный |
| Италия | 4 | Серия A, B, C1, C2 |
| **Россия** | **2** | **Премьер-лига, Первый дивизион** |

Второго дивизиона в этом списке нет — поэтому он и не появлялся в игре, что бы
мы ни писали в `.dat`. Уровни в базе (2 → 3) на список играбельных лиг не влияют.

При этом сам `fm.exe` про зоны Второго дивизиона знает — во второй таблице
(`call 0xd35180`) они перечислены вместе с числом команд:

| id | Соревнование | Команд | Параметр вызова |
|---|---|---|---|
| 130486 | Премьер-лига | 16 | −2 |
| 130487 | Первый дивизион | 22 | −2 |
| 130488 | Второй дивизион - Запад | 16 | −1 |
| 130489 | Второй дивизион - Центр | 16 | −1 |
| 130490 | Второй дивизион - Юг | 13 | −1 |
| 130491 | Второй дивизион - Восток | 10 | −1 |
| 8055759 | Второй дивизион - Урал/Волга | 12 | −1 |

### Позднее чтение трёхсловного массива: частичный след

Статический просмотр `fm.exe` показывает, что `0xd690a0` инициализирует объект
с контейнером по `+0x30` и vtable `0x15f50a0`. Регистрация `0xd63c10` кладёт
в такой контейнер запись из трёх DWORD: ID соревнования, ступень и байтовый флаг
(в `0xd67240` она добавляется как 12-байтовый элемент). Vtable-метод
`0xd660e0` копирует элемент по индексу.

Найден и более поздний потребитель **такого же типа** контейнера: `0xd657b0`
проходит список, получает элемент через virtual slot `+0x2c` (`0xd660e0`),
передаёт первое DWORD в lookup `0xc21500`, а для найденного объекта проверяет
virtual-метод `+0x74`. Это доказывает, что похожие трёхсловные записи позднее
используются как ключи объектов, но пока не доказано, что рассматриваемый
`0xd657b0` читает именно список регистрации нации: он берёт контейнер из другого
владельца (`[obj+0x28]+0x30`). Поэтому связь с выбором клубов или дублей остаётся
гипотезой. Новых игровых патчей на этом основании не собирали.

## Сопоставление с Испанией: третий уровень

В исходном `fm.exe` для Испании на ступени 2 зарегистрирован **один ID**:
`121091` («Испания. Второй дивизион B»). Отдельная таблица сведений при этом
содержит четыре групповых ID — `69`, `70`, `71`, `72` («B1»–«B4»), каждый с
числом 20 и параметром `−2`. В базе у `69`–`71` обычные записи соревнований с
уровнем 2. Запись `72` есть в обеих таблицах, но имеет маркер
`00 00 00 ff 7f c5 6e c5 6e` и уровень 0, поэтому стандартный сканер её
пропускает. Сам `121091` тоже пропускает стандартный маркер `activate.py`, но
в базе есть отдельная запись с альтернативным маркером; её поле уровня равно 100.

Российская структура отличается: штатная таблица сведений перечисляет пять
зон напрямую (`130488`–`130491`, `8055759`) с параметром `−1` и значениями
16/16/13/10/12; у четырёх записей `130488`–`130491` уровень базы равен 2,
а `8055759` имеет обычный маркер соревнования и уровень 0. Это похоже на
испанскую группу `72` только по уровню 0: у `72` маркер другой. Общий ID
`8051008` также имеет уровень 100, но оформлен обычным маркером записи
соревнования. То есть у
обоих стран есть ID-«зонтик» с уровнем 100, однако их тип записи различается;
одного совпадения уровня и имени недостаточно, чтобы считать их эквивалентными.
У Испании на ступень 2 зарегистрирован `121091`, а отдельные строки сведений
описывают группы `69`–`72`. В России штатные строки сведений перечисляют зоны
напрямую, а не `8051008`. DB-уровень испанских групп `69`–`71` — 2, как и у
российских `130488`–`130491`; неуспешный same-tier пакет выставлял российским
зонам уровень 3. Регистрация одного `8051008` уже проверялась — команды не
появились. Поэтому структурная аналогия подтверждена, но она не даёт прямого
рабочего патча. Одиночная замена российского параметра `−1` на `−2` скрывала
Россию в проверенном эксперименте.

### Что ещё видно в связях базы

Скрипт `compare_group_links.py` находит в `server_db.dat` записи вида
`03 <ID группы> 04 <ID связанного соревнования>`. Они есть и у испанских групп
`69–72`, и у российских зон. Например, у B1 чаще встречаются ID испанской
Третьей лиги `67023616` (группа 7) и `67023621` (группа 12); у российской зоны
«Запад» — `8050940` (Москва), `8050902` (Северо-Запад), `8050901` (Золотое
кольцо) и `8050900` (Центральная группа 1). Это подтверждает, что в базе есть
структурированные связи между уровнями, а не только названия лиг.

Проверка контекста подтвердила, что некоторые пары лежат внутри сериализованных
записей с названиями клубов: например, на смещении `2479110` в распакованном
`server_db.dat` стоит `03 <130488> 04 <8050940>`, а через 49 байт начинается
UTF-16LE-название `Sportakademclub Moscow`. Значит, это действительно клубная
связь с зоной/соревнованием, а не только сводный список названий.

Но это **не прямой список участников Второго дивизиона**: тот же тип пары
встречается у `Dinamo Moscow`, клуба верхнего уровня. Это совместимо с гипотезой,
что запись первой команды может ссылаться на лигу её дубля, например на
Московский третий дивизион. Эвристический поиск читаемых названий рядом с парами даёт
72 для «Запада», 59 для «Центра», 92 для «Юга», 45 для «Востока» и 52 для
«Урала/Волги» — существенно больше EXE-счётчиков 16/16/13/10/12. У большинства
испанских групп подсказок по названиям тоже больше 20 (B3 — исключение: 18).

В анализатор добавлены контрольные соревнования: Россия Первый дивизион (`130487`),
испанские Первый и Второй дивизионы (`67`, `68`). Для них не найдено ни одной пары
этого типа; в то же время для испанских групп `69–72` найдено 20–178 совпадений,
а для российских зон — 45–106. Значит, `03/04` не является универсальным
представлением списка участников обычной лиги. Это сужает область поиска, но
само по себе не доказывает, что речь именно о резервах.

Эти подсказки могут отражать региональные и резервные связи, а не участников
конкретного сезона. Поля `03/04` пока нельзя использовать как список участников первой команды.
Точное игровое назначение полей ещё не установлено. Числа скрипта —
эвристические подсказки по строкам и бинарные вхождения, **не число уникальных
участников**.

### Проверка идеи «ID клуба вместо ID турнира»

Добавлен read-only скрипт `check_team_ids_in_competition_links.py`. Он взял 44
точных ID клубов из CSV Второго дивизиона 2007 года и 34 ID родительских/
резервных команд из связанных `(D)`-записей: всего 74 уникальных ID. Ни один из
них не найден ни в позиции `03 <ID> 04`, ни в позиции `03 <other ID> 04 <ID>`
в `server_db.dat`. В этих парах обнаруженные ID разрешаются как соревнования;
проверка не говорит, что клубных ID нет в каких-либо других полях базы.

В EXE `0xd63c10` добавляет в список нации трёхсловную запись с ID соревнования,
ступенью и флагом. Отдельный путь `0xd35180`, используемый для сведений о лигах,
по этому ID ищет объект и работает с полями диапазонов соревнования. Поэтому
подставить ID клуба вместо ID чемпионата — **не подтверждённый способ добавить
команду**: это передаст в путь регистрации турнира ключ другого объекта, а не
создаст связь «клуб участвует в чемпионате». Возможное поведение такой неверной
подстановки в самой игре не проверялось; новый игровой патч не собирался.
Нужно найти поле/таблицу состава, где ожидаются именно ID клубов, и установить,
как движок связывает этот список с зарегистрированным турниром.

Запуск проверки:

```bash
python3 fm2008/dbpatch/check_team_ids_in_competition_links.py --db /path/to/db
```

### Сверка CSV Второго дивизиона 2007 года

Добавлен read-only анализатор `compare_roster_regions.py` и тесты
`tests/test_compare_roster_regions.py`. Он предпочитает точную полную строку
из CSV и проверяет окончание UTF-16 записи. Если найден только вариант с `(Д)`,
он помечается как возможный дубль, а не засчитывается как первая команда.
Английское имя подбирается по тому же ID и транслитерации; ссылка `03/04`
принимается, только если маркеры находятся ровно за 48 или 49 байт до начала
имени. Теперь анализатор также проверяет, находится ли ID клуба в пределах
512 байт после найденной пары, и печатает смещение `ID+N B`. Это ID-соседство,
а не автоматически распознанная граница записи. Пример запуска:

```bash
python3 fm2008/dbpatch/compare_roster_regions.py --db /path/to/db
python3 fm2008/dbpatch/tests/test_compare_roster_regions.py

# проверить связанные записи `(D)` и лиги, на которые они указывают
python3 fm2008/dbpatch/compare_reserve_links.py --db /path/to/db
python3 fm2008/dbpatch/tests/test_compare_reserve_links.py
python3 fm2008/dbpatch/compare_lower_roster_links.py --db /path/to/db
python3 fm2008/dbpatch/tests/test_compare_lower_roster_links.py
```

После отсева резервных вариантов получено 42 сопоставления первых команд из
72: у 29 найдена пара с ожидаемой зоной, у 2 — с другой зоной, у 11 пара не
найдена. Для 27 строк полного названия не нашлось, для 2 ID не подобралось
достаточно похожее английское имя, а для «Ротора» найден только вариант
`Rotor Volgograd (D)`, который анализатор не принимает за первую команду.
Ранее он ошибочно считался матчем; «Черноморец Новороссийск» теперь сначала
сопоставляется с точным именем первой команды, а не с вариантом `(D)`. Это
по-прежнему предварительный результат, не список участников и не основание для
патча. Транслитерационный порог и точное назначение ссылок `03/04` требуют
независимой проверки.

Отдельно проверил именно ID команды, а не только строку названия: во всех 31
найденных парах `03/04` для ростера ID клуба встречается далее по `server_db.dat`
через 130–251 байт (например, «Спортакадемклуб Москва», ID `130523`: пара на
`0x25d406`, ID — на `0x25d4c2`, разница 188 байт). Это подтверждает, что ID —
полезный ключ для обратного поиска и связывает найденную пару с окрестностью
конкретной клубной записи. Но 512-байтовое окно не декодирует границы записи и
само по себе не доказывает, что пара задаёт текущего участника соревнования.

Разобрал эти две «другие зоны» точнее: у Волги Ульяновск пара
`130489 → 8050904` (Второй дивизион — Центр → Третий дивизион — Волга), у
Зенита Челябинск — `130491 → 8050907` (Второй дивизион — Восток → Третий
дивизион — Урал). Оба lower-ID действительно являются названиями соответствующих
третьих дивизионов в `lang_db`; сами пары стоят на штатном 49-байтовом смещении.
Они не ведут к ожидаемой для этих клубов группе `8055759` «Урал-Поволжье».
В сочетании с уже найденной такой же парой у московского клуба высшего уровня
(«Динамо Москва» → Запад / Третий дивизион — Москва) это поддерживает трактовку
`03/04` как региональных или межуровневых связей, но не как списка текущих
участников. Почему первые ID у двух уральско-поволжских клубов отличаются от
ожидаемой группы, пока не установлено.

### Гипотеза: пары связывают клуб с его дублем

Эта гипотеза получила конкретную поддержку. В английском потоке `lang_db`
найдено 99 уникальных названий с суффиксом `(D)`; у 17 соответствующих
основных названий есть пара `03/04`, причём `04` указывает на один из российских
Третьих дивизионов. Все эти 17 вариантов `(D)` также присутствуют в `server_db`;
сама пара стоит у записи `(D)` только для `Lada Togliatti`, а в остальных 16
случаях — только у основного имени.

Теперь анализатор выводит ID обеих сущностей. Для всех 17 случаев ID родителя
отличается от ID `(D)`-варианта, и ближайшее вхождение ID родителя находится
через 148–317 байт после его пары. Например, у `Dinamo Moscow` это parent ID
`1520`, reserve ID `476093`, пара `130488 → 8050940` и смещение `ID+317B`.
Только у «Лады» пара найдена и у отдельной записи резерва: parent ID `1524`
(`ID+217B`), reserve ID `477603` (`ID+140B`). Это сильнее привязывает пару к
ID конкретной клубной записи, но не устанавливает, какую команду клуба она
регистрирует. В отчёте `ID+N` остаётся проверкой соседства байтов, не декодером
границ записи.

Связь согласуется с независимым ростером Третьей лиги 2007 года:

- `Volga Uljanovsk` → `8050904` («Третий дивизион — Волга»); в
  `fm2008/third-league-russia/data/clubs_2007.csv` есть «Волга-2-Энергия»,
  Ульяновск, зона «Приволжье».
- `Lada Togliatti (D)` → `8050904`; в том же ростере есть «Лада-2», Тольятти.
- `KamAZ Naberezhnye Chelny` (у клуба есть вариант `(D)`) → `8050904`; там же
  есть «КАМАЗ-2», Набережные Челны.
- Основная запись `Alania Vladikavkaz` → `8050903`; у клуба есть вариант `(D)`,
  а в ростере — «Алания-2», Владикавказ. Аналогично, основная запись
  `Zhemchuzhina Sochi` ссылается на Третий дивизион Юг, а в ЮФО есть
  «Жемчужина-А» из Сочи.

Есть и более точные совпадения в CSV Второго дивизиона 2007 года: у самой
записи первой команды ссылка `04` совпадает с регионом её резерва в CSV Третьей
лиги:

| Клуб Второго дивизиона | Пара в базе | Резерв в CSV Третьей лиги |
|---|---|---|
| Спортакадемклуб Москва | `130488 → 8050940` (Москва) | Спортакадемклуб-2, Москва |
| Спартак Кострома | `130488 → 8050901` (Золотое кольцо) | Спартак-2, Кострома |
| Динамо Вологда | `130488 → 8050901` (Золотое кольцо) | Динамо-2, Вологда |
| Волга Тверь | `130488 → 8050901` (Золотое кольцо) | Волга-2, Тверь |
| Волга Ульяновск | `130489 → 8050904` (Волга) | Волга-2-Энергия, Ульяновск |
| Амур Благовещенск | `130491 → 8050905` (Дальний Восток) | Амур-2, Благовещенск |

Особенно полезен пример «Динамо-2» Вологда: эта резервная команда есть в базе
(`fm2008_match.csv`: `club_in_db=да`), но пара стоит у основной записи
`Dinamo Vologda` и не находится перед именем `Dinamo-2 Vologda`. У «Лады» пара
одинакова в записях `Lada Togliatti` и `Lada Togliatti (D)`. Это похоже на
связь основной команды с резервной лигой, хотя сами значения поля ещё не
расшифрованы.

У пяти из этих шести клубов первый ID `03` также совпадает с зоной Второго
дивизиона в CSV; исключение — Волга Ульяновск (`130489` вместо `8055759`).
Это усиливает рабочую модель: `03` может указывать на регион/группу основной
команды, а `04` — на дивизион дубля. Это всё ещё не доказывает, что игра
использует пару именно так.

Дополнительный скрипт `compare_lower_roster_links.py` сопоставляет все 31 клуба
с парой из Второго дивизиона по городу и зоне `04`: у 10 нашлась команда в той
же нижней зоне; у 6 название совпадает с основой клуба (`-2`/дубль), а у 4 это
другие местные команды. Например, у «Олимпии» Волгоград это УОР, у
«Судостроителя» Астрахань — «Волгарь-Газпром-2», у «Автодора» Владикавказ —
«Алания-2», у «Динамо» Барнаул — «Полимер». Таким образом, `04` устойчиво
указывает на региональный нижний дивизион, но не всегда на резерв именно этого
клуба.

Независимый контроль среди клубов Первого дивизиона 2007 даёт тот же рисунок:
«Шинник» → Запад / Третий дивизион — Золотое кольцо (в ростере есть
«Шинник-2-Водоканал»), «Звезда» Иркутск → Восток / Сибирь («Звезда-2»),
«СКА-Энергия» → Восток / Дальний Восток («СКА-Энергия-2»), «Авангард» Курск →
Центр / Черноземье («Авангард-2») и «Текстильщик» Иваново → Запад / Золотое
кольцо («Текстильщик-2»). Это делает трактовку `04` как лиги дубля ещё
правдоподобнее, одновременно подтверждая, что пара `03/04` не означает, что
основная команда играет именно в указанной нижней лиге.

Это согласуется с гипотезой, что `03/04` может связывать основной клуб с
соревнованием дубля. Но это пока корреляция: `fm2008/third-league-russia/data/fm2008_match.csv`
помечает ряд точных названий резервных команд (`Лада-2`, `КАМАЗ-2`,
`Волга-2-Энергия`, `Алания-2`, `Спортакадемклуб-2`) как отсутствующие в базе;
«Динамо-2» Вологда, напротив, отмечено как имеющееся. Есть и контрпример:
`Zenit-2 St. Petersburg` сам имеет пару `130488 → 8050902` (Запад → Северо-Запад),
но в CSV Третьей лиги 2007 нет резервной команды «Зенит» из Санкт-Петербурга;
основной `Zenit St. Petersburg` и вариант `(D)` есть в базе, но пары у них нет.
Поэтому совпадение клуба, города и группы не доказывает, что `04` указывает
именно на конкретную резервную команду. Полного соответствия по всем 99 именам
нет, а более общая географическая связь остаётся возможной; считать пару
доказанной записью о регистрации дубля или первой команды пока рано. В частности, связь Волги
Ульяновск с `8050904` объясняет «Волгу-2-Энергию», но не объясняет, почему
первый ID в паре — `130489` («Центр»), а не `8055759` («Урал-Поволжье»).

Скрипт выводит также главное различие родительских записей: ID `121091` у
Испании имеет специальный маркер `00 00 00 90 00 c5 6e ff 01`, а ID `8051008`
у России — обычный маркер `00 00 00 ff 7f 8c`; поле уровня у обоих равно 100.
Это ближайшая найденная структурная разница, но её роль ещё нужно подтвердить
до нового патча. Диагностический скрипт теперь выводит также поля `+36/+40`:
у трёх российских зон они ненулевые (Запад `18520/1443`, Центр `15333/1693`,
Юг `93927/1700`), а у Востока и Урала/Волги — `0/0`. При этом у обеих последних
зон всё равно есть клубные региональные связи `03/04`, поэтому эти поля нельзя
считать единственным условием наличия таких связей. Их значение пока неизвестно.

### Проверенный неудачный эксперимент: родитель + групповые параметры

Пакет [`ready/fm2008-second-division-parent-groups-test.zip`](ready/fm2008-second-division-parent-groups-test.zip)
проверен пользователем: **Россия пропала из списка выбора чемпионатов**.
Пакет регистрировал `8051008` на ступени 2, менял параметры пяти зон в
info-таблице с `−1` на `−2` и оставлял DB-файлы без изменений. **Не использовать.**

Это показывает, что менять `−1` на `−2` как признак играбельности нельзя.
Дизассемблирование функции `0xd35180` уточняет причину: значение `−2`
подменяется переданным рядом числом команд, а `−1` сохраняется как отдельное
значение; результат записывается в пару 16-битных полей. Это параметр диапазона,
а не простой переключатель «играбельно/неиграбельно». Родительский ID `8051008`
отдельно тоже проверялся — команды не добавил. После двух свежих тестов вывод
тот же: параметры групп сами по себе не приводят к загрузке клубов. Следующий
этап — трассировка источника состава клубов и того, как он связывается с ID
зарегистрированных дивизионов; новые изменения диапазонов не использовать.

### Новая сверка формата регистрации групп

Вызовы `0xd63c10` принимают третий параметр как однобайтовый флаг и передают его
в менеджер страны. В штатном коде Испания B зарегистрирована как
`121091 / tier 2 / flag 4`; Норвегия. Второй дивизион — как
`145428 / tier 2 / flag 4`. Их дочерние группы не регистрируются вызовами
`0xd63c10`: они отдельно перечислены через `0xd35180` (у Испании — ID `69–72`,
по 20 команд, диапазонный параметр `−2`; у Норвегии — восемь групп `1300603–1300610`,
по 14 команд, `−2`). Российская функция не содержит регистрации ступени 2;
она передаёт сведения о пяти зональных ID с их штатными числами команд и
параметром `−1`.

Это не расшифровывает флаг `4`, но показывает, что прошлый тест с родительским
ID `8051008` на флаге `0` не повторял структуру двух штатных grouped-league
примеров в исполняемом файле. При этом DB-запись российского ID `8051008` отличается от примеров:
обычный маркер и уровень 100; у испанского родителя специальный маркер и тоже
уровень 100, у норвежского — обычный маркер и уровень 2. Поэтому это лишь
обоснование для изолированного теста, не доказательство решения.

Собран диагностический архив
[`ready/fm2008-second-division-flag4-parent-probe.zip`](ready/fm2008-second-division-flag4-parent-probe.zip):
он добавляет только `8051008 / tier 2 / flag 4`, повторно исполняет штатную
регистрацию Первого дивизиона и не меняет ни одного DB-файла, параметра зоны
или клуба. Для сборки и статической проверки:

```bash
python3 fm2008/dbpatch/build_flag4_parent_probe.py --exe /path/to/fm.exe
python3 fm2008/dbpatch/tests/test_si_db.py
```

Пользователь проверил архив на базе 8.0.2: **Россия и пять зон появились,
но клубов в них нет**. Значит, регистрация зон состоялась, но тест не добавил
команды.

Затем проверен архив
[`ready/fm2008-second-division-flag4-fixed-groups-probe.zip`](ready/fm2008-second-division-flag4-fixed-groups-probe.zip):
он сохранял `8051008 / tier 2 / flag 4` и менял пять параметров `−1 → −2`, не
меняя числа команд `16/16/13/10/12`, DB-файлы или клубы. Результат пользователя:
**Россия пропала**. Значит, `−2` нельзя переносить на российские строки сведений;
этот архив оставлен только для воспроизводимости, не использовать.

По дизассемблированию `0xd35180`, `−2` подставляет рядом переданное число в
верхнюю границу пары 16-битных полей, а `−1` становится `65535`. Испанские и
норвежские группы поэтому получают фиксированные границы (`20..20` и `14..14`),
российские — открытые (`16..65535`, `13..65535` и т. д.). Хотя такой контраст
виден в коде, игровой тест доказал, что копировать фиксированные границы в
российские строки нельзя.

Дополнительное дизассемблирование уточнило роль `flag 4`: wrapper `0xd63c10`
собирает ID соревнования, ступень и однобайтовый флаг в 12-байтовую запись;
первый метод таблицы страны (`0xd67240`) просто добавляет эту запись в массив.
На этом этапе флаг не включает загрузку клубов. Теперь нужно трассировать
дальнейшее использование этих записей и отдельный источник состава клубов.

## Что делает `patch.py`

Операции в JSON, каждая — с **ожидаемыми** байтами:

| Тип | Смысл |
|---|---|
| `assert` | проверить байты по смещению |
| `write_bytes` | заменить байты (длина обязана совпадать) |
| `write_u32` | заменить число |
| `rename_string` | переименовать строку в `lang_db.dat` **без сдвига таблицы** |

Гарантии:

- при несовпадении `expect` патч **не применяется** — скрипт останавливается;
- оригинал не трогается, изменённые файлы пишутся в `out/`, копия — `*.orig`;
- после записи файл читается заново и сверяется с ожидаемым результатом;
- `--dry-run` прогоняет все проверки без записи.

Проверено на реальной базе: попытка переименовать «Второй дивизион» честно
останавливается, потому что строка встречается 82 раза — так и задумано.

## Как устроен патч `activate.py`

У каждого соревнования в базе есть запись фиксированного размера. Начало записи
находится по подписи `00 00 00 ff 7f 8c` — сразу после `u32 id`:

```
+0  ...          +8   u32 id      +12 подпись 00 00 00 ff 7f 8c
+23 u8 уровень   +36  u32 ссылка  +40 u32 ссылка
```

Уровни России в исходной базе:

| Соревнование | Уровень |
|---|---|
| Премьер-лига | 1 |
| Первый дивизион | 2 |
| **Второй дивизион (6 зон)** | **2 — тот же, что у Первого** |
| Третий дивизион (11 зон) | 3 |

То есть Второй дивизион не «следующая ступень», а дубль второго уровня. Патч
ставит зонам свой уровень 3, а Третьему — 4, чтобы ступени не пересекались.

```bash
python3 activate.py --db "/путь/data/db" --report "Россия"      # что в базе сейчас
python3 activate.py --db "/путь/data/db" --variant pyramid --dry-run
python3 activate.py --db "/путь/data/db" --variant pyramid --out out --zip
```

Скрипт сам находит записи, требует ожидаемый байт на каждом месте (иначе
отказывается работать), после записи перечитывает файл и проверяет, что
изменились ровно запланированные байты. Ничего не сдвигается по длине.

Проверено на реальной базе 8.0.2: 12 правок в `second3`, 34 в `pyramid`.

Правка уровней в базе сама по себе не активировала российский Второй дивизион.
В игровом EXE подтверждён отдельный путь регистрации соревнований; тест
`8051008 / tier 2 / flag 4` делает Россию и зоны видимыми, но не добавляет
участников. Перенос клубов отвергнут и не рассматривается как решение.

Пока не установлен конкретный, подтверждённый DB-параметр или путь кода,
который назначает клубы участникам российского Второго дивизиона. Поэтому
финальное решение и «рабочий патч» не заявляются. Нужны отдельные
контролируемые тесты в новой карьере на оригинальной базе 8.0.2; результат
проверки в FM2008 должен сообщить пользователь.

## Календарь и появление участников: первичная проверка EXE

Проверены экспортные точки FM08 8.0.2 для России:

- `rus_setup_comps` — `0xE8C8E0`;
- `rus_setup_fixture_rules` — `0xE8CC30`;
- `rus_setup_transfer_rules` — `0xE8D8C0`.

То есть настройка соревнований и настройка fixture rules — отдельные вызовы.
Отдельный экспорт `rus_get_minimum_division_teams` (`0xE8BB90`) задаёт
сведения о дивизионах/числе команд; российские fixture rules уже описаны
в EXE, включая ссылки на основные соревнования и зоны `130488`–`130491`.
В теле `rus_setup_fixture_rules` видны многочисленные вызовы общих функций
настройки правил и параметры соревнований/сезона. В частности, функция 47 раз
вызывает общий helper `0xDC6560`; тот читает числовые параметры, рассчитывает
производное значение из 16-битного параметра, создаёт объект размером `0x18`
байт и передаёт его в коллекцию. Это похоже на добавление календарных/fixture-
правил, а не на запись списка матчей с парами клубов. В пределах экспортной
fixture-функции не найден прямой вызов lookup `0xC21500`, а в непосредственных
аргументах `push imm32` нет ни одного из 74 известных ID клубов (точные ID из
ростера Второго дивизиона 2007 и связанные parent/reserve ID). Это ограниченная
проверка прямого кода: она не доказывает, что данные не могут поступать через
косвенный вызов или из базы.

В таблице экспортов есть отдельные `*_register_teams_for_comps`-функции у ряда
стран, но такой экспорт для России отсутствует. У Норвегии также есть
`nor_setup_fixture_rules`, но нет отдельного `nor_register_teams_for_comps`.
Это показывает, что отсутствие специального хука не уникально для России и не
доказывает отсутствие регистрации российских клубов вообще: она может идти
общим путём из базы.
Однако на данный момент нет признаков, что российская fixture-настройка сама
назначает команды. Поэтому вручную составлять календарь как способ «добавить»
участников пока не обосновано. По диагностике `FIXTURE_MANAGER::create_next_fixtures_list`
разобран helper `0xDA9C00` (lookup) и часть функции `0xDA9C50` (обработка дат и
fixture-записей). Она сравнивает competition ID и вызывает методы через vtable;
в просмотренном коде явного перечисления клубов нет. Caller около `0x75B2A0`
формирует параметры и обрабатывает возвращённые объекты, но смысл виртуальных
методов ещё не установлен. Это не даёт права заключать, что календарь никак не
влияет на выбор участников.

### Диагностический патч: одна зона напрямую

Создан `ready/fm2008-second-division-west-single-zone-probe.zip`. Он сохраняет
штатную регистрацию Первого дивизиона и дополнительно регистрирует только Запад
(ID `130488`) на ступени 2 с флагом 4. Остальные зоны, DB и fixture rules не
меняются; клубы не перемещаются. Пользователь проверил тест: Россия/зона
появилась, но клубов нет. Пользователь уточнил результат в терминах режима:
Россия выбирается при создании карьеры, чемпионат Второго дивизиона проводится
в симуляции, но управлять клубом там нельзя, а игроки подгружаются не полностью.
Также отсутствует вкладка/графа статистики игроков. Это подтверждает, что тест
добавил видимость/симуляцию зоны, но не сделал её полноценным playable tier;
прямая регистрация группы сама по себе не создаёт полный состав клубов/игроков.
Отдельный переключатель или DB-связь, отвечающие за playable status и полную
загрузку, пока не установлены. Тест не менял календарь и не является решением.
В архиве лежат `fm.exe`, инструкция и SHA-256; для любого повтора нужна новая
карьера и исходный EXE версии 8.0.2, после теста его нужно восстановить.

### Отдельный путь специальных регистраций

В `esp_register_teams_for_comps` (`0xEC8250`) код ищет объект по ID `1305519` и
передаёт в общий helper `0xC9AB70` два entity ID (`1759`, `1736`), значение
`2007` и флаг `1`. Во французском callback используется ID `1305504`, пять
entity ID (`2008`, `2062`, `2069`, `2010`, `854`), значение `2007` и флаг `0`.
Helper разрешает первый ID через коллекцию объектов и добавляет запись с
указателем на объект, 16-битным значением и байтовым флагом. По имени callback
это специальная регистрация команд для соревнований, но связь этого механизма
с составами обычных дивизионов не установлена; ID менеджеров не найдены как
записи соревнований в распакованных `client_db.dat`/`server_db.dat`. Поэтому
копировать этот вызов в российскую настройку пока нельзя.

Следующий шаг — проследить dispatcher специальных callback-ов и общий путь,
который строит состав клубов для обычного соревнования, сравнив рабочую
групповую лигу с российской. Для интерпретации UI полезно уточнить, где именно
виден выбор: Россия как управляемая страна в создании карьеры или только
соревнование в списке лиг базы.
