# dbpatch — патчер базы FM2008

Код для работы с `*.dat` базы Football Manager 2008: чтение контейнера, сверка,
безопасные правки на уровне байтов и поиск соревнований по названию.

Всё проверено на реальной базе **8.0.2** из папки `db` (файлы из `inbox/1.zip … 4.zip`).

## Патч и проверка

В папке [`ready/`](ready/) — готовые файлы. В каждом архиве лежит папка `db/`.

| Архив | Что внутри | Зачем |
|---|---|---|
| `fm2008-second-division-pyramid.zip` | `client_db.dat`, `server_db.dat` с уровнями 1-2-3-4 | сам патч |
| `fm2008-diagnostic-lang.zip` | `lang_db.dat`, где «Россия. Премьер-лига» стала «Россия. ПРЕМЬЕР-ЛИГА» | **проверка, что игра вообще читает наши файлы** |

Диагностический файл нужен, потому что «ничего не поменялось» бывает по трём
разным причинам: игра взяла кэш, файлы легли не в ту папку, или в базе нет
такого признака. Переименование видно сразу, поэтому оно отвечает на вопрос.

### Порядок проверки

1. Закрыть игру.
2. Удалить кэш: `Документы\Sports Interactive\Football Manager 2008\cache`
   (папку `cache` целиком; игра создаст её заново).
3. Положить все три файла в папку базы — туда, где лежит `802.xml`
   (обычно `...\Football Manager 2008\data\db\802\`), с заменой.
   Перед заменой скопировать оригиналы в сторонку — это и есть откат.
4. Запустить игру → **Новая игра** → выбрать лиги → Россия.

Что это значит:

| Видно «ПРЕМЬЕР-ЛИГА» | Видно «Второй дивизион» | Вывод |
|---|---|---|
| да | да | патч сработал |
| да | нет | файлы читаются, но признак играбельности в базе не в уровне — ищем дальше |
| нет | нет | игра не увидела файлы: кэш или не та папка |

## Быстрый старт

```bash
cd fm2008/dbpatch

# 1. что вообще есть в базе по России
python3 hunt.py --db "/путь/к/Football Manager 2008/data/db" --list-competitions

# 2. где лежит конкретное соревнование
python3 hunt.py --db ... --competition "Россия. Второй дивизион - Волга"

# 3. сравнить играбельное и неиграбельное (поиск флага активности)
python3 hunt.py --db ... --diff "Россия. Первый дивизион" "Россия. Второй дивизион - Волга"

# 4. применить патч (сначала всегда с --dry-run)
python3 patch.py examples/plan.example.json --db ... --dry-run
python3 patch.py examples/plan.example.json --db ... --out out

# 5. тесты
python3 tests/test_si_db.py
```

Полный список — [`data/competitions_ru.csv`](data/competitions_ru.csv) (25 записей).

Это важная поправка к более раннему выводу: я искал буквально «Третья лига», а в
базе эти соревнования называются **«Третий дивизион - <зона>»**. Они существуют и
описаны в базе, но помечены как неиграбельные.

**Где лежат ссылки на соревнование.** ID встречается в `client_db.dat` и
`server_db.dat` в структуре вида:

```
<u32 0xb7> <u32 id_соревнования> 00 00 00 ff 7f 8c 00 00 00 00 00 00 00 00 <u32 A> 00 00 00 00 <u8 B> 02 00 00 00 a5 00 00 00 ff ff ff ff
```

Сравнение `--diff` «Премьер-лига» vs «Второй дивизион - Волга» даёт расхождения
именно в полях `A` (`8` против `4`) и `B` (`01` против `02`) — это первые
кандидаты на «уровень/статус» соревнования. Окна байтов печатает `hunt.py --diff`.

## Что делает `patch.py`

Операции в JSON, каждая — с **ожидаемыми** байтами:

| Тип | Смысл |
|---|---|
| `assert` | проверить байты по смещению |
| `write_bytes` | заменить байты (длина обязана совпадать) |
| `write_u32` | заменить число |
| `rename_string` | переименовать строку в `lang_db.dat` **без сдвига таблицы** |

Гарантии:

- при несовпадении `expect` патч **не применяется** — скрипт останавливается;
- оригинал не трогается, изменённые файлы пишутся в `out/`, копия — `*.orig`;
- после записи файл читается заново и сверяется с ожидаемым результатом;
- `--dry-run` прогоняет все проверки без записи.

Проверено на реальной базе: попытка переименовать «Второй дивизион» честно
останавливается, потому что строка встречается 82 раза — так и задумано.

## Как устроен патч `activate.py`

У каждого соревнования в базе есть запись фиксированного размера. Начало записи
находится по подписи `00 00 00 ff 7f 8c` — сразу после `u32 id`:

```
+0  ...          +8   u32 id      +12 подпись 00 00 00 ff 7f 8c
+23 u8 уровень   +36  u32 ссылка  +40 u32 ссылка
```

Уровни России в исходной базе:

| Соревнование | Уровень |
|---|---|
| Премьер-лига | 1 |
| Первый дивизион | 2 |
| **Второй дивизион (6 зон)** | **2 — тот же, что у Первого** |
| Третий дивизион (11 зон) | 3 |

То есть Второй дивизион не «следующая ступень», а дубль второго уровня. Патч
ставит зонам свой уровень 3, а Третьему — 4, чтобы ступени не пересекались.

```bash
python3 activate.py --db "/путь/data/db" --report "Россия"      # что в базе сейчас
python3 activate.py --db "/путь/data/db" --variant pyramid --dry-run
python3 activate.py --db "/путь/data/db" --variant pyramid --out out --zip
```

Скрипт сам находит записи, требует ожидаемый байт на каждом месте (иначе
отказывается работать), после записи перечитывает файл и проверяет, что
изменились ровно запланированные байты. Ничего не сдвигается по длине.

Проверено на реальной базе 8.0.2: 12 правок в `second3`, 34 в `pyramid`.

## Чего ещё нет и почему

Чтобы Второй дивизион **стал играбельным**, нужно поменять признак неиграбельности
в записи соревнования. Для этого осталось:

1. сравнить две записи **одного уровня** — активную и неактивную (например,
   «Чехия. Первый дивизион» и «Чехия. Третий дивизион CFL»), чтобы отделить
   «уровень» от «статуса»;
2. собрать патч по найденным смещениям;
3. проверить в игре — а запустить FM2008 в этой песочнице нельзя (нет Windows,
   нет Wine, базы для редактора тоже нет). Поэтому финальную проверку делает
   человек на своём ПК: один `.dat` подменяется, игра запускается, смотрится,
   появился ли дивизион.

Всё, что нужно для шагов 1–2, здесь есть: чтение, поиск по ID, дифф, безопасная
запись и тесты. Шаг 3 — за вами, и я разберу результат.
