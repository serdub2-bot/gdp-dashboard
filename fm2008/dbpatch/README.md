# dbpatch — патчер базы FM2008

Код для работы с `*.dat` базы Football Manager 2008: чтение контейнера, сверка,
безопасные правки на уровне байтов и поиск соревнований по названию.

Всё проверено на реальной базе **8.0.2** из папки `db` (файлы из `inbox/1.zip … 4.zip`).

## Почему база не помогала: список дивизионов зашит в fm.exe

Проверено на самой игре 8.0.2. Для каждой страны в `fm.exe` есть функция,
которая регистрирует играбельные дивизионы по порядку:

```asm
push 0              ; флаги
push 1              ; ступень
push 0x1fdb7        ; id = 130487 «Россия. Первый дивизион»
mov  ecx, <нация>
call 0xd63c10       ; регистрация дивизиона
```

Вызовов столько, сколько играбельных ступеней у страны:

| Страна | Зарегистрировано | Ступени |
|---|---|---|
| Англия | 6 | Премьер, Первый, Второй, Третий, Конференция, Конференция Север/Юг |
| Испания | 3 | Первый, Второй, Второй B |
| Германия | 3 | Бундеслига, Второй, Региональный |
| Италия | 4 | Серия A, B, C1, C2 |
| **Россия** | **2** | **Премьер-лига, Первый дивизион** |

Второго дивизиона в этом списке нет — поэтому он и не появлялся в игре, что бы
мы ни писали в `.dat`. Уровни в базе (2 → 3) на список играбельных лиг не влияют.

При этом сам `fm.exe` про зоны Второго дивизиона знает — во второй таблице
(`call 0xd35180`) они перечислены вместе с числом команд:

| id | Соревнование | Команд | Параметр вызова |
|---|---|---|---|
| 130486 | Премьер-лига | 16 | −2 |
| 130487 | Первый дивизион | 22 | −2 |
| 130488 | Второй дивизион - Запад | 16 | −1 |
| 130489 | Второй дивизион - Центр | 16 | −1 |
| 130490 | Второй дивизион - Юг | 13 | −1 |
| 130491 | Второй дивизион - Восток | 10 | −1 |
| 8055759 | Второй дивизион - Урал/Волга | 12 | −1 |

## Сопоставление с Испанией: третий уровень

В исходном `fm.exe` для Испании на ступени 2 зарегистрирован **один ID**:
`121091` («Испания. Второй дивизион B»). Отдельная таблица сведений при этом
содержит четыре групповых ID — `69`, `70`, `71`, `72` («B1»–«B4»), каждый с
числом 20 и параметром `−2`. В базе у `69`–`71` обычные записи соревнований с
уровнем 2. Запись `72` есть в обеих таблицах, но имеет маркер
`00 00 00 ff 7f c5 6e c5 6e` и уровень 0, поэтому стандартный сканер её
пропускает. Сам `121091` тоже пропускает стандартный маркер `activate.py`, но
в базе есть отдельная запись с альтернативным маркером; её поле уровня равно 100.

Российская структура отличается: штатная таблица сведений перечисляет пять
зон напрямую (`130488`–`130491`, `8055759`) с параметром `−1` и значениями
16/16/13/10/12; у четырёх записей `130488`–`130491` уровень базы равен 2,
а `8055759` имеет обычный маркер соревнования и уровень 0. Это похоже на
испанскую группу `72` только по уровню 0: у `72` маркер другой. Общий ID
`8051008` также имеет уровень 100, но оформлен обычным маркером записи
соревнования. То есть у
обоих стран есть ID-«зонтик» с уровнем 100, однако их тип записи различается;
одного совпадения уровня и имени недостаточно, чтобы считать их эквивалентными.
У Испании на ступень 2 зарегистрирован `121091`, а отдельные строки сведений
описывают группы `69`–`72`. В России штатные строки сведений перечисляют зоны
напрямую, а не `8051008`. DB-уровень испанских групп `69`–`71` — 2, как и у
российских `130488`–`130491`; неуспешный same-tier пакет выставлял российским
зонам уровень 3. Регистрация одного `8051008` уже проверялась — команды не
появились. Поэтому структурная аналогия подтверждена, но она не даёт прямого
рабочего патча. Одиночная замена российского параметра `−1` на `−2` скрывала
Россию в проверенном эксперименте.

### Что ещё видно в связях базы

Скрипт `compare_group_links.py` находит в `server_db.dat` записи вида
`03 <ID группы> 04 <ID связанного соревнования>`. Они есть и у испанских групп
`69–72`, и у российских зон. Например, у B1 чаще встречаются ID испанской
Третьей лиги `67023616` (группа 7) и `67023621` (группа 12); у российской зоны
«Запад» — `8050940` (Москва), `8050902` (Северо-Запад), `8050901` (Золотое
кольцо) и `8050900` (Центральная группа 1). Это подтверждает, что в базе есть
структурированные связи между уровнями, а не только названия лиг.

Проверка контекста подтвердила, что некоторые пары лежат внутри сериализованных
записей с названиями клубов: например, на смещении `2479110` в распакованном
`server_db.dat` стоит `03 <130488> 04 <8050940>`, а через 49 байт начинается
UTF-16LE-название `Sportakademclub Moscow`. Значит, это действительно клубная
связь с зоной/соревнованием, а не только сводный список названий.

Но это **не прямой список участников Второго дивизиона**: тот же тип пары
встречается у `Dinamo Moscow`, клуба верхнего уровня. Это совместимо с гипотезой,
что запись первой команды может ссылаться на лигу её дубля, например на
Московский третий дивизион. Эвристический поиск читаемых названий рядом с парами даёт
72 для «Запада», 59 для «Центра», 92 для «Юга», 45 для «Востока» и 52 для
«Урала/Волги» — существенно больше EXE-счётчиков 16/16/13/10/12. У большинства
испанских групп подсказок по названиям тоже больше 20 (B3 — исключение: 18).
Эти подсказки могут отражать региональные и резервные связи, а не участников
конкретного сезона. Поля `03/04` пока нельзя использовать как список участников первой команды.
Возможная связь с дублями проверяется отдельно; точное игровое назначение
полей ещё не установлено. Числа скрипта —
эвристические подсказки по строкам и бинарные вхождения, **не число уникальных
участников**.

### Сверка CSV Второго дивизиона 2007 года

Добавлен read-only анализатор `compare_roster_regions.py` и тесты
`tests/test_compare_roster_regions.py`. Он предпочитает точную полную строку
из CSV и проверяет окончание UTF-16 записи. Если найден только вариант с `(Д)`,
он помечается как возможный дубль, а не засчитывается как первая команда.
Английское имя подбирается по тому же ID и транслитерации; ссылка `03/04`
принимается, только если маркеры находятся ровно за 48 или 49 байт до начала
имени. Пример запуска:

```bash
python3 fm2008/dbpatch/compare_roster_regions.py --db /path/to/db
python3 fm2008/dbpatch/tests/test_compare_roster_regions.py
```

После отсева резервных вариантов получено 42 сопоставления первых команд из
72: у 29 найдена пара с ожидаемой зоной, у 2 — с другой зоной, у 11 пара не
найдена. Для 27 строк полного названия не нашлось, для 2 ID не подобралось
достаточно похожее английское имя, а для «Ротора» найден только вариант
`Rotor Volgograd (D)`, который анализатор не принимает за первую команду.
Ранее он ошибочно считался матчем; «Черноморец Новороссийск» теперь сначала
сопоставляется с точным именем первой команды, а не с вариантом `(D)`. Это
по-прежнему предварительный результат, не список участников и не основание для
патча. Транслитерационный порог и точное назначение ссылок `03/04` требуют
независимой проверки.

Разобрал эти две «другие зоны» точнее: у Волги Ульяновск пара
`130489 → 8050904` (Второй дивизион — Центр → Третий дивизион — Волга), у
Зенита Челябинск — `130491 → 8050907` (Второй дивизион — Восток → Третий
дивизион — Урал). Оба lower-ID действительно являются названиями соответствующих
третьих дивизионов в `lang_db`; сами пары стоят на штатном 49-байтовом смещении.
Они не ведут к ожидаемой для этих клубов группе `8055759` «Урал-Поволжье».
В сочетании с уже найденной такой же парой у московского клуба высшего уровня
(«Динамо Москва» → Запад / Третий дивизион — Москва) это поддерживает трактовку
`03/04` как региональных или межуровневых связей, но не как списка текущих
участников. Почему первые ID у двух уральско-поволжских клубов отличаются от
ожидаемой группы, пока не установлено.

### Гипотеза: пары связывают клуб с его дублем

Эта гипотеза получила конкретную поддержку. В английском потоке `lang_db`
найдено 99 уникальных названий с суффиксом `(D)`; у 17 соответствующих названий
основной команды есть пара `03/04`, причём `04` указывает на один из российских
Третьих дивизионов. Пара обычно стоит в записи основного имени, а не в записи
`(D)`; исключение среди проверенных названий — `Lada Togliatti (D)`.

Связь согласуется с независимым ростером Третьей лиги 2007 года:

- `Volga Uljanovsk` → `8050904` («Третий дивизион — Волга»); в
  `fm2008/third-league-russia/data/clubs_2007.csv` есть «Волга-2-Энергия»,
  Ульяновск, зона «Приволжье».
- `Lada Togliatti (D)` → `8050904`; в том же ростере есть «Лада-2», Тольятти.
- `KamAZ Naberezhnye Chelny` (у клуба есть вариант `(D)`) → `8050904`; там же
  есть «КАМАЗ-2», Набережные Челны.
- Основная запись `Alania Vladikavkaz` → `8050903`; у клуба есть вариант `(D)`,
  а в ростере — «Алания-2», Владикавказ. Аналогично, основная запись
  `Zhemchuzhina Sochi` ссылается на Третий дивизион Юг, а в ЮФО есть
  «Жемчужина-А» из Сочи.

Это уже больше, чем простое совпадение географии: нижние ID и названия дублей
сходятся с конкретными резервными командами из ростера 2007 года. Рабочая
гипотеза теперь такая: `03/04` может связывать основной клуб с соревнованием,
где играет его дубль. Но полного соответствия по всем 99 именам нет, а поля
могут описывать также региональные ассоциации; считать пару доказанной записью
о регистрации дубля или первой команды пока рано. В частности, связь Волги
Ульяновск с `8050904` объясняет «Волгу-2-Энергию», но не объясняет, почему
первый ID в паре — `130489` («Центр»), а не `8055759` («Урал-Поволжье»).

Скрипт выводит также главное различие родительских записей: ID `121091` у
Испании имеет специальный маркер `00 00 00 90 00 c5 6e ff 01`, а ID `8051008`
у России — обычный маркер `00 00 00 ff 7f 8c`; поле уровня у обоих равно 100.
Это ближайшая найденная структурная разница, но её роль ещё нужно подтвердить
до нового патча. Диагностический скрипт теперь выводит также поля `+36/+40`:
у трёх российских зон они ненулевые (Запад `18520/1443`, Центр `15333/1693`,
Юг `93927/1700`), а у Востока и Урала/Волги — `0/0`. При этом у обеих последних
зон всё равно есть клубные региональные связи `03/04`, поэтому эти поля нельзя
считать единственным условием наличия таких связей. Их значение пока неизвестно.

### Контроль: Португалия B

Проверил ещё одну штатную много-групповую лигу, чтобы не переносить маркер
Испании на Россию вслепую. Португалия тоже регистрирует один родительский ID
`126964` на ступени 2 и отдельные группы `62`–`64`. У родителя уровень базы 2
и маркер `00 00 00 5a 01 c0 7f 5a 01`; у групп маркер
`00 00 00 06 02 00 70 06 02` (уровни 2/2/3). В отличие от Испании и России,
для групп `62`–`64` в `server_db` нет ссылок формата `03 <group> 04 <comp>`.
Это показывает, что маркеры и клубные связи различаются между схемами групп;
механически копировать испанскую запись или считать пару `03/04` универсальным
списком участников нельзя.

## Статус: активация не решена

Игровые тесты пользователя показали:

1. Регистрация пяти зон как ступеней 2–6: названия видны, команд нет.
2. Совместная правка уровней базы с последовательными ступенями: команд нет.
3. Регистрация общего ID 8051008: команд нет.
4. Замена параметров `-1` на `-2` скрыла Россию.

Вариант [`ready/fm2008-second-division-same-tier.zip`](ready/fm2008-second-division-same-tier.zip)
проверен пользователем: **команды не появились**. Он регистрирует пять зон как
параллельные группы одной ступени 2 и ставит их уровень в базе равным 3.
Этот эксперимент не считать решением; статические тесты подтверждают только
структуру файлов, не поведение игры.

### Проверенный неудачный эксперимент: родитель + групповые параметры

Пакет [`ready/fm2008-second-division-parent-groups-test.zip`](ready/fm2008-second-division-parent-groups-test.zip)
проверен пользователем: **Россия пропала из списка выбора чемпионатов**.
Пакет регистрировал `8051008` на ступени 2, менял параметры пяти зон в
info-таблице с `−1` на `−2` и оставлял DB-файлы без изменений. **Не использовать.**

Это показывает, что менять `−1` на `−2` как признак играбельности нельзя.
Дизассемблирование функции `0xd35180` уточняет причину: значение `−2`
подменяется переданным рядом числом команд, а `−1` сохраняется как отдельное
значение; результат записывается в пару 16-битных полей. Это параметр диапазона,
а не простой переключатель «играбельно/неиграбельно». Родительский ID `8051008`
отдельно тоже проверялся — команды не добавил. До выяснения связи между
родительской записью и зональными клубными данными новый игровой пакет не
собирать.

## Быстрый старт

```bash
cd fm2008/dbpatch

# 1. что вообще есть в базе по России
python3 hunt.py --db "/путь/к/Football Manager 2008/data/db" --list-competitions

# 2. где лежит конкретное соревнование
python3 hunt.py --db ... --competition "Россия. Второй дивизион - Волга"

# 3. сравнить играбельное и неиграбельное (поиск флага активности)
python3 hunt.py --db ... --diff "Россия. Первый дивизион" "Россия. Второй дивизион - Волга"

# 4. применить патч (сначала всегда с --dry-run)
python3 patch.py examples/plan.example.json --db ... --dry-run
python3 patch.py examples/plan.example.json --db ... --out out

# 5. тесты
python3 tests/test_si_db.py
python3 tests/test_compare_group_links.py
```

Полный список — [`data/competitions_ru.csv`](data/competitions_ru.csv) (25 записей).

Это важная поправка к более раннему выводу: я искал буквально «Третья лига», а в
базе эти соревнования называются **«Третий дивизион - <зона>»**. Они существуют и
описаны в базе, но помечены как неиграбельные.

**Где лежат ссылки на соревнование.** ID встречается в `client_db.dat` и
`server_db.dat` в структуре вида:

```
<u32 0xb7> <u32 id_соревнования> 00 00 00 ff 7f 8c 00 00 00 00 00 00 00 00 <u32 A> 00 00 00 00 <u8 B> 02 00 00 00 a5 00 00 00 ff ff ff ff
```

Сравнение `--diff` «Премьер-лига» vs «Второй дивизион - Волга» даёт расхождения
именно в полях `A` (`8` против `4`) и `B` (`01` против `02`) — это первые
кандидаты на «уровень/статус» соревнования. Окна байтов печатает `hunt.py --diff`.

## Что делает `patch.py`

Операции в JSON, каждая — с **ожидаемыми** байтами:

| Тип | Смысл |
|---|---|
| `assert` | проверить байты по смещению |
| `write_bytes` | заменить байты (длина обязана совпадать) |
| `write_u32` | заменить число |
| `rename_string` | переименовать строку в `lang_db.dat` **без сдвига таблицы** |

Гарантии:

- при несовпадении `expect` патч **не применяется** — скрипт останавливается;
- оригинал не трогается, изменённые файлы пишутся в `out/`, копия — `*.orig`;
- после записи файл читается заново и сверяется с ожидаемым результатом;
- `--dry-run` прогоняет все проверки без записи.

Проверено на реальной базе: попытка переименовать «Второй дивизион» честно
останавливается, потому что строка встречается 82 раза — так и задумано.

## Как устроен патч `activate.py`

У каждого соревнования в базе есть запись фиксированного размера. Начало записи
находится по подписи `00 00 00 ff 7f 8c` — сразу после `u32 id`:

```
+0  ...          +8   u32 id      +12 подпись 00 00 00 ff 7f 8c
+23 u8 уровень   +36  u32 ссылка  +40 u32 ссылка
```

Уровни России в исходной базе:

| Соревнование | Уровень |
|---|---|
| Премьер-лига | 1 |
| Первый дивизион | 2 |
| **Второй дивизион (6 зон)** | **2 — тот же, что у Первого** |
| Третий дивизион (11 зон) | 3 |

То есть Второй дивизион не «следующая ступень», а дубль второго уровня. Патч
ставит зонам свой уровень 3, а Третьему — 4, чтобы ступени не пересекались.

```bash
python3 activate.py --db "/путь/data/db" --report "Россия"      # что в базе сейчас
python3 activate.py --db "/путь/data/db" --variant pyramid --dry-run
python3 activate.py --db "/путь/data/db" --variant pyramid --out out --zip
```

Скрипт сам находит записи, требует ожидаемый байт на каждом месте (иначе
отказывается работать), после записи перечитывает файл и проверяет, что
изменились ровно запланированные байты. Ничего не сдвигается по длине.

Проверено на реальной базе 8.0.2: 12 правок в `second3`, 34 в `pyramid`.

## Чего ещё нет и почему

Чтобы Второй дивизион **стал играбельным**, нужно поменять признак неиграбельности
в записи соревнования. Для этого осталось:

1. сравнить две записи **одного уровня** — активную и неактивную (например,
   «Чехия. Первый дивизион» и «Чехия. Третий дивизион CFL»), чтобы отделить
   «уровень» от «статуса»;
2. собрать патч по найденным смещениям;
3. проверить в игре — а запустить FM2008 в этой песочнице нельзя (нет Windows,
   нет Wine, базы для редактора тоже нет). Поэтому финальную проверку делает
   человек на своём ПК: один `.dat` подменяется, игра запускается, смотрится,
   появился ли дивизион.

Всё, что нужно для шагов 1–2, здесь есть: чтение, поиск по ID, дифф, безопасная
запись и тесты. Шаг 3 — за вами, и я разберу результат.
